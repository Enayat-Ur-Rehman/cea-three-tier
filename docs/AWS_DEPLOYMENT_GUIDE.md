# AWS Deployment Guide (step by step)

This guide deploys the three-tier task tracker to a personal AWS account with Terraform and GitHub Actions. Every command runs from the repository root unless a step says otherwise.

Cost note: while it runs, the stack costs about $5 per day (NAT gateway, two ALBs, four t3.micro hosts, one db.t3.micro, CloudFront). Destroy it when the demo is over (step 10).

---

## 0. What you need

| Tool | Why |
|---|---|
| AWS account with an IAM user or role that can create VPC, EC2, ELB, RDS, ECR, IAM, CloudFront, SSM, Secrets Manager and CloudWatch resources | Terraform runs as this identity |
| AWS CLI v2 | credentials and checks |
| Terraform 1.5 or newer | builds the infrastructure |
| GitHub account and `gh` CLI | hosts the code and runs the pipeline |
| Docker | local run and local tests |

Configure a named profile once, then use it everywhere:

```bash
aws configure --profile cea-deployer       # region us-east-1
export AWS_PROFILE=cea-deployer
aws sts get-caller-identity                 # must print your account, not an error
```

## 1. Run it locally first

```bash
cp .env.example .env                        # set two local passwords
docker compose up -d --build
pytest app/tests                            # unit tests
E2E_BASE_URL=http://localhost:8080 pytest tests/e2e
bash scripts/check_segmentation.sh          # web tier must NOT reach MySQL
```

Open http://localhost:8080. Stop with `docker compose down -v`.

---

## 2. Terraform settings

```bash
cd infra/terraform
cp terraform.tfvars.example terraform.tfvars
```

Set `github_repo = "<owner>/<repo>"` in `terraform.tfvars`. Terraform uses it to create the GitHub OIDC deploy role. That role trusts only the `main` branch of that one repository, so GitHub never needs stored AWS keys.

---

## 3. Phase 1: registry, release pointers and the deploy role

The servers pull their image at boot, so the images must exist before the servers do. Phase 1 creates only what the pipeline needs to push images:

```bash
terraform init
terraform apply \
  -target=aws_ecr_repository.web -target=aws_ecr_repository.app \
  -target=aws_ssm_parameter.image_tag \
  -target=aws_iam_openid_connect_provider.github \
  -target=aws_iam_role.github_deploy -target=aws_iam_role_policy.github_deploy
terraform output -raw deploy_role_arn
```

---

## 4. Put the code on GitHub and connect the pipeline

```bash
gh repo create <owner>/<repo> --public --source . --remote origin
gh variable set AWS_DEPLOY_ROLE_ARN --body "<deploy_role_arn from step 3>"
gh variable set AWS_REGION --body us-east-1
git push -u origin main
```

The push starts the pipeline. **Test** runs unit tests, starts all three tiers with Docker Compose, runs the end-to-end tests through Nginx and checks network segmentation. **Build and push** builds both images and pushes them to ECR tagged with the commit SHA. **Deploy** writes the SHA into SSM Parameter Store and starts an instance refresh. On this first run there are no servers yet, so the refresh and the smoke test are skipped.

Check that SSM now holds a 40-character SHA, not `not-built-yet`:

```bash
aws ssm get-parameter --name /cea/app/image_tag --query Parameter.Value --output text
```

---

## 5. Phase 2: everything else

```bash
cd infra/terraform
terraform apply                             # about 20 to 25 minutes (RDS and CloudFront are the slow parts)
terraform output app_url                    # https://<id>.cloudfront.net
```

Wait until both target groups show all targets **healthy** (EC2, Target groups), then open `app_url`.

Then re-run the pipeline once (Actions, CI/CD, Run workflow). This time it performs a real rolling deploy and the smoke test checks over HTTPS that the database connection uses TLS.

---

## 6. What protects what

| Control | Where |
|---|---|
| HTTPS for users | CloudFront default certificate, HTTP redirects to HTTPS |
| Only CloudFront can reach the public ALB | ALB security group allows only the CloudFront origin-facing prefix list, and the listener returns 403 unless the secret `X-Origin-Verify` header is present |
| Web tier cannot reach the database | `cea-sg-db` accepts 3306 only from `cea-sg-app` |
| Database not on the internet | RDS in isolated subnets with no route to the internet, `publicly_accessible = false` |
| Encryption at rest | RDS storage encrypted (KMS) |
| Encryption in transit to the database | parameter group sets `require_secure_transport = 1`, the app verifies the RDS CA |
| No passwords in code | password generated by Terraform, stored in Secrets Manager, read by the app role at start |
| No stored CI keys | GitHub OIDC role, credentials expire after one hour |
| Immutable releases | ECR tags are immutable, every image is tagged with its git SHA |

## 7. Test elasticity with the load test

```bash
docker run --rm -i -e BASE_URL="$(terraform -chdir=infra/terraform output -raw app_url)" \
  grafana/k6:0.54.0 run - < loadtest/k6.js
```

The script seeds 300 tasks, holds 120 virtual users for 12 minutes and deletes the seeded tasks at the end. Watch **EC2, Auto Scaling Groups, cea-app-asg, Activity**: CPU passes the 50% target, the target tracking alarm fires and the group launches new hosts. About 15 minutes after the test ends, the group scales back in to 2.

---

## 8. Test availability (self-healing)

1. **EC2, Instances**, select one `cea-web` instance, **Instance state, Terminate**.
2. Keep refreshing the app: the other web host keeps serving.
3. Within a few minutes the ASG launches a replacement (Activity tab).

---

## 9. Roll back

A failed instance refresh rolls back on its own. If the smoke test fails after a deploy, the pipeline restores the previous SHA in SSM, refreshes both groups again and marks the run red.

---

## 10. Tear down (do not skip)

```bash
cd infra/terraform
terraform destroy                           # CloudFront takes 10 to 15 minutes to disable and delete
```

Then delete the deployer access key in IAM if it is no longer needed.

## 11. Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| Target group `unhealthy` for a long time | user data still running, or image pull failed | Session Manager into the host, `sudo cat /var/log/user-data.log`, `sudo docker ps -a`, `sudo docker logs web` (or `app`) |
| CloudFront URL shows 403 | request reached the ALB without the origin header, or the distribution is still deploying | wait for the distribution status `Deployed` |
| CloudFront URL shows 502 or 504 | no healthy web targets | check the web target group and `sudo docker logs web` |
| `/api/health/db` returns 503 | app cannot reach RDS, the secret, or TLS failed | RDS must be Available; `sudo docker logs app` |
| Pipeline: `Not authorized to perform sts:AssumeRoleWithWebIdentity` | wrong `AWS_DEPLOY_ROLE_ARN`, or `github_repo` does not match the repository | fix the variable or `github_repo`, apply phase 1 again |
| Pipeline: `An Instance Refresh is already in progress` | two deploys overlapped | the script cancels the old refresh; re-run the job |
| Secret name already scheduled for deletion | an earlier destroy | `aws secretsmanager delete-secret --secret-id cea/db-credentials --force-delete-without-recovery` |

AWS Academy Learner Lab note: Learner Lab cannot create IAM roles. Set `existing_instance_profile = "LabInstanceProfile"` and leave `github_repo` empty. No OIDC role is created then, so the deploy jobs cannot run from GitHub.
